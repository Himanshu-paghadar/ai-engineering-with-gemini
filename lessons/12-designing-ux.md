# Lesson 12 — Designing UX for AI Applications

> Source: `12-designing-ux-for-ai-applications`

## 🎯 Goal
Design AI apps people can, and want to, use — with trust calibrated correctly.

---

## 1. Four qualities of a good AI UX

| Quality | Meaning | Failure mode |
|---|---|---|
| **Useful** | Functionality matches the intended purpose | A grader that doesn't grade accurately |
| **Reliable** | Performs consistently, errors handled | Silent failures; no recovery path |
| **Accessible** | Usable by people of all abilities | Keyboard-inaccessible, no screen-reader support |
| **Pleasant** | Enjoyable to use | Blunt error messages; no sense of progress |

> Not every problem needs AI. AI should **augment** the experience — automating manual work or personalizing it.

## 2. Trust: the two failure directions

```
Mistrust  ←———————— calibrated trust ————————→  Overtrust
(user rejects the app)                    (user stops checking the output)
```

**Overtrust example:** a teacher stops proofreading AI-assigned grades → unfair grades, missed feedback.
Both extremes are design failures, not user failures.

### Lever 1 — Explainability
- Make clear the output is **AI-generated, not human**.
  - ❌ "Start chatting with your tutor now"
  - ✅ "Use an AI tutor that adapts to your needs and helps you learn at your pace"
- Show **how** the system reached the output (sources, reasoning, confidence).
- Explain **persona limits** — a student account may get guidance toward an answer rather than the answer.
- **Simplify the explanation.** Your users are not AI experts.

### Lever 2 — Control
- Let users shape the request: format, tone, length.
- Let users **edit the output** after generation.
- Let users **opt in/out** of what data the AI uses (their notes, teacher resources).
- Deliberately add a little **friction** between prompt and result — a reminder that this is a machine.

## 3. Collaboration & feedback
- Build a **feedback loop** — even a thumbs up/down. It improves the system and builds trust.
- **Communicate capabilities and limits** explicitly.
- **Handle out-of-scope requests gracefully**:
  > "Sorry, this product was trained on History and Math, so I can't answer a Geography question."

### In Python: design the failure paths, not just the happy path

```python
r = client.interactions.create(model=MODEL, system_instruction=SYSTEM, input=user_text)

text = r.output_text
if not text:
    # safety filter, recitation block, or empty generation
    text = ("I couldn't answer that one. Try rephrasing it, "
            "or ask me something about History or Math.")

print(text)
print("\n— Generated by AI. Please double-check important facts.")
```

Three UX surfaces worth wiring up from day one:
1. **Disclosure** — a persistent "AI-generated" marker.
2. **Escape hatch** — a way to reach a human or a source document.
3. **Feedback capture** — store the prompt, response and rating for later evaluation (lesson 14).

## 4. Assignment checklist
- **Pleasant** — explanations everywhere? encouraging exploration? kind error wording?
- **Usability** — navigable by mouse *and* keyboard?
- **Trust & transparency** — a human in the loop to verify output?
- **Control** — can users opt in/out of data collection?

---

## 🧠 Crux Notes
- Target **calibrated trust** — mistrust and overtrust are both design failures.
- **Explainability + control** are the two levers that produce trust.
- Say "AI" in the copy. Hiding it feels smart and destroys trust when discovered.
- Design the **empty/blocked/out-of-scope** response deliberately; it will happen constantly.
- A feedback loop is cheap to build and is the only honest input to your evaluation later.

## 🛠️ Practical Task

**Build:** `practice/12_ux_review.md` + `practice/12_improved_chat.py`

### Part A — Audit (write-up)
Take your `practice/07_chat.py` and score it 1–5 on each of the four qualities, with one concrete
justification each. Then list every failure path a user could hit (blocked response, rate limit,
off-topic question, network error) and what the user currently sees.

### Part B — Fix (code)
Improve the chat app with:
1. **Disclosure** — a persistent "AI-generated, verify important facts" marker.
2. **Control** — `/tone formal|casual`, `/length short|detailed` commands that alter the system instruction.
3. **Feedback** — after each response accept `+`/`-` and append the rating to `practice/12_feedback.jsonl`.
4. **Graceful scope handling** — a clear, kind message naming what it *can* help with.
5. **Keyboard-friendly** — `Ctrl+C` exits cleanly with a goodbye, not a traceback.

### Passing criteria

| # | Criterion | How to verify |
|---|---|---|
| 1 | Disclosure on every response | Not just at startup |
| 2 | `/tone formal` visibly changes output | Compare the same question before and after |
| 3 | Ratings persist | `wc -l practice/12_feedback.jsonl` grows |
| 4 | Out-of-scope message names capabilities | Ask about something excluded |
| 5 | `Ctrl+C` exits code 0 with a message | No `KeyboardInterrupt` traceback |
| 6 | Audit covers all 4 qualities + failure paths | Read the markdown |

### Verify
```bash
printf 'What is 2+2?\n+\n/tone formal\nWhat is 2+2?\n-\nexit\n' | python practice/12_improved_chat.py
wc -l practice/12_feedback.jsonl   # expect 2
```

**The point of Part A:** you cannot improve UX you have not named. Writing down what the user sees when things fail is most of the work.
